# Deterministic content-addressed cook runtime and float determinism limits

Context: PLAN.md Bet 3 says `key = H(op id + version, params, input hashes, seeds, backend-class)`, a CPU reference backend that defines truth, GPU results tagged by backend-class, and CI that re-cooks and compares hashes. Gate (c) of Phase 1 requires identical hashes on another machine. These notes test that against the literature. Items I could not source are listed under Gaps and not asserted.

## 1. Build/incremental systems: what to copy for a content-addressed, incremental cook cache

### Takeaway
Two mechanisms are needed and are separable: a verifying/early-cutoff layer for incremental recompute (Salsa-style backdating, Shake verifying traces, Buck2 DICE), and a constructive-trace layer (Bazel action cache plus CAS, Nix CA derivations) that makes results shareable across machines. Our `key = H(...)` over input hashes is a constructive trace. Early cutoff is only effective if outputs are hashed by content.

### Cited Findings
- Build Systems a la Carte splits build systems by rebuild decision (dirty bit, verifying traces, constructive traces) and scheduler. Shake uses verifying traces; Bazel and CloudBuild use constructive traces; Buck and Nix are placed under deep constructive traces. Early cutoff, static vs dynamic dependencies, local vs cloud and deterministic vs non-deterministic tasks are listed as separate axes. The paper's "Cloud Shake" combines Shake and Bazel strengths. — [Mokhov blog on the paper](https://blogs.ncl.ac.uk/andreymokhov/build-systems-a-la-carte/), [paper PDF](https://www.microsoft.com/en-us/research/uploads/prod/2018/03/build-systems-a-la-carte.pdf)
- Verifying trace stores hashes of a task's dependencies from the last run and recomputes and compares them. A constructive trace is keyed by the hash of the result as well as inputs, so it works as a cache (Hash r = h). — [Hackage `build` Trace docs](https://hackage.haskell.org/package/build-1.0/docs/Build-Trace.html)
- Bazel remote cache has two stores: an action cache (`/ac/`, action hash -> action result metadata) and a CAS (`/cas/`, output blobs by SHA256). Flow: local reuse, remote lookup, run on miss, upload. — [Bazel remote caching](https://bazel.build/remote/caching)
- Bazel action key is inputs, output names, command line and explicitly passed env vars; untracked tools (different `/usr/bin` compilers) or differing `$PATH` produce wrong hits or missed sharing. Lesson: every input that can change a result must be in the key, and nothing else should be. — [Bazel remote caching](https://bazel.build/remote/caching)
- Salsa red-green: a global revision counter increments on each input set; each memoized function stores its dependencies and the revision they last changed. If none changed, reuse. If re-run produces an equal result, Salsa "backdates" it so downstream callers see no change (early cutoff). Durability levels let functions that depend only on high-durability inputs skip dependency walks. — [Salsa algorithm reference](https://salsa-rs.github.io/salsa/reference/algorithm.html)
- Nix: floating content-addressed derivations name outputs by content hash, so an upstream change that leaves output bytes identical leaves downstream paths unchanged and avoids rebuilds. Still experimental (`ca-derivations`). Self-referencing outputs need a provisional path, which is an impurity, and non-determinism can be checked by building more than once. Fixed-output derivations declare the hash up front and must have no references. — [Nix manual, content-addressed outputs](https://nix.dev/manual/nix/stable/store/derivation/outputs/content-address.html)
- Guix-devel discussion (non-authoritative) notes Nix lacks early cutoff unless using constructive traces with depth 1. — [Guix-devel thread](https://lists.gnu.org/r/guix-devel/2021-03/msg00581.html)
- Buck2 hashes command plus inputs into a digest and checks the RE action cache; DICE is its incremental engine (slides list invalidation, efficient recomputation, early cutoff, concurrent requests). Deferred materialization avoids downloading intermediates, reported about 2.5x faster for RE-heavy builds, but requires action cache TTL > TTL of every referenced artifact, and does not work with open-source RE backends that do not expose TTLs. — [Buck2 deferred materialization](https://buck2.build/docs/users/advanced/deferred_materialization/), [Modern DICE slides](https://buck2.build/assets/Modern_DICE.pdf)
- Unreal DDC: hierarchical (local + shared), UE 5.4+ uses Zen Storage Server over HTTP, which Epic describes as unauthenticated and to be kept on a trusted network/VPN; Zen handles GC. Read-only PAK and S3 archive tiers exist. — [Epic DDC docs](https://dev.epicgames.com/documentation/unreal-engine/using-derived-data-cache-in-unreal-engine) (search summary; I did not find the key-hash format).
- Houdini PDG/TOPs caching is file-based: per-node Cache Mode (Automatic / Automatic ignore upstream / Read Files / Write Files); work item states Clean, DirtyMissing, DirtyStale, DirtyAlways. A node that generates different work items dirties everything downstream. TOPs does not check input/output file contents, so replacing an intermediate file does not dirty dependents. Output paths need `@` attribute tokens so PDG can predict the file. This is existence/timestamp-driven, not content-addressed. — [Houdini cooking docs](https://www.sidefx.com/docs/houdini/tops/cooking.html), [work item cache state](https://www.sidefx.com/docs/houdini/tops/pdg/workItemCacheState.html), [ROP Fetch](https://www.sidefx.com/docs/houdini/nodes/top/ropfetch.html)
- BLAKE3 is a Merkle tree internally, highly parallel across threads and SIMD lanes, supports incremental updates and verified streaming (Bao); Rust crate has SSE2/SSE4.1/AVX2/AVX-512/NEON/WASM implementations with runtime detection and a `rayon` feature. Says "much faster" than SHA-2/SHA-3/BLAKE2, `b3sum` an order of magnitude faster than `sha256sum`. No throughput numbers on the page. — [BLAKE3 repo](https://github.com/BLAKE3-team/BLAKE3)
- FastCDC (Xia et al., ATC 2016): gear-hash content-defined chunking about 10x faster than Rabin CDC and about 3x faster than other Gear/AE CDC with near-identical dedup ratio; techniques are simplified hash judgment, cut-point skipping, normalized chunk sizes. — [USENIX ATC16 FastCDC](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia)

### Inferences
- Use both layers: an in-memory Salsa-like graph (revision, backdating, durability: e.g. imported assets high, live params low) for interactive recompute, and a persistent action-cache (key -> output hash) plus CAS for cross-session/cross-machine sharing. The cook output hash is what enables early cutoff; a param change that yields byte-identical geometry (e.g. a clamped noise amplitude) stops propagation.
- Houdini's TOPs shows the failure mode to avoid: existence/timestamp-based invalidation misses content changes. Our approach (hash everything, including file inputs by content) fixes this but requires importers to hash source files as inputs.
- Key hygiene (Bazel's lesson): the key should contain only declared inputs plus op version, backend-class and a toolchain/ABI stamp. Anything undeclared (env vars, wall clock, thread count, CPU features) must not influence results, and anything that does must be in the key or banned.
- Granularity: whole-geo keys are cheap and robust; per-tile/per-column keys give finer reuse. A reasonable layout is a two-level scheme: node-level action key (whole-geo) mapping to a Merkle manifest of per-column, per-chunk hashes. Sub-geo dependency declarations (per-point/per-tile) then only decide which chunks must be recomputed; the output is still addressed by chunk. This matches Bet 2 (`Arc`'d column chunks) so unchanged columns share storage and hashes for free.
- Hash cost: BLAKE3 (tree, SIMD, parallel) is the natural content hash for chunk blobs and manifests; hash fixed-size column chunks (e.g. 64K to 1M elements) in parallel and combine as a Merkle tree so that a one-chunk edit rehashes one chunk plus the path to the root. Use a fast non-crypto hash (xxh3) only for in-process dedup where adversaries are out of scope. Content-defined chunking (FastCDC) is probably unnecessary for fixed-stride columnar data because point indices are stable; it matters for opaque blobs (imported meshes, textures, serialized graphs) where insertions shift bytes.

### Gaps
- No sourced numbers for BLAKE3 GB/s on this hardware; benchmark ourselves.
- Did not find primary sources for Adapton, Differential Dataflow, or Shake internals beyond the Build Systems paper; did not fetch Salsa's older "red-green" origin in rustc.
- Houdini's SOP-level cook cache (non-PDG) internals are not publicly documented in what I retrieved.
- Unreal DDC key derivation (versioned GUID + content hash) not confirmed.
- Arrow / Parquet / Zarr chunking and checksum conventions were not researched in this pass (Zarr chunk grid and Arrow IPC buffer layout are the obvious references).

## 2. Float determinism: IEEE-754 pitfalls and what Rust/LLVM guarantee

### Takeaway
IEEE 754 makes +, -, *, /, sqrt (and fused multiply-add when explicit) bit-exact; everything else (transcendentals, contraction, reassociation, NaN payloads) is implementation-dependent. Rust documents this honestly: `sin/cos/exp/powi` precision is explicitly non-deterministic, `mul_add` is exact and guaranteed stable, and NaN bits are not portable.

### Cited Findings
- Rust `f32::mul_add` computes with a single rounding, "guaranteed to be the rounded infinite-precision result", specified by IEEE 754 `fusedMultiplyAdd` and "guaranteed not to change"; it may be slow on targets without a hardware FMA. — [Rust f32 docs](https://doc.rust-lang.org/std/primitive.f32.html)
- Rust `powi`, `powf`, `sin`, `cos`, `exp` have "Unspecified precision": non-deterministic, varying by platform, Rust version, "and can even differ within the same execution from one invocation to the next." `algebraic_*` operators likewise may differ between invocations in one run. — [Rust f32 docs](https://doc.rust-lang.org/std/primitive.f32.html)
- NaN: arithmetic NaN sign, quiet bit and payload are chosen non-deterministically; results are not guaranteed portable. Optimizations (`f * 1.0` -> `f`) can change NaN bits; `(0.0/0.0).is_sign_positive()` can differ by architecture/opt level. Rust follows LLVM rules, not IEEE, here, and does not support changed rounding modes or observable FP status bits. — [Rust RFC 3514](https://rust-lang.github.io/rfcs/3514-float-semantics.html), [rust-lang/rust#129567](https://github.com/rust-lang/rust/issues/129567)
- Gaffer on Games: only basic operations are bit-exact; sources of divergence are compiler optimization, x87 80-bit intermediates (and control words changed by DLLs), FMA (auto-generated by compilers; PowerPC vs Intel), transcendentals differing between AMD and Intel, and library behavior. Recommends SSE2, strict FP modes, pinned x87 precision, and notes cross-machine determinism is possible with same compiler/ISA and controls but is not settled. — [Gaffer on Games, Floating Point Determinism](https://gafferongames.com/post/floating_point_determinism/)
- The `libm` crate is a port of MUSL libm (archived; merged into `compiler-builtins`); its page makes no accuracy or cross-platform bit-exactness claims. — [rust-lang/libm](https://github.com/rust-lang/libm)
- Rust's default build does not enable fast-math (Rust has no global fast-math flag; `algebraic_*` methods are opt-in per operation) — [Rust f32 docs](https://doc.rust-lang.org/std/primitive.f32.html) (inferred from the algebraic-operators section; I did not fetch an explicit statement about LLVM contraction defaults).

### Inferences
- Because LLVM on Rust does not contract `a*b+c` into FMA unless `mul_add` is written, plain Rust f32 code is more reproducible across CPUs than default C++ builds; but this should be a tested invariant (CI on x86-64 and aarch64), not assumed, since the sourced docs here do not state the contraction default explicitly.
- All transcendentals in the reference path must come from a pinned, in-repo implementation (port of `libm`/MUSL pinned by version, or own polynomial kernels using only +,-,*,/,`mul_add`,sqrt). Never call `f32::sin` etc. in a hashed path. Box2D, Rapier and Burst all converged on this (section 4).
- Treat NaN as an error value for cook outputs (validate/canonicalize NaN before hashing) because NaN payloads are not portable; also canonicalize -0.0 vs 0.0 if equality semantics need it, and flush or define subnormal behavior (Burst flushes subnormals).

### Gaps
- No primary source retrieved on `-ffp-contract` defaults in rustc/LLVM, x87 relevance on 64-bit targets, or `target-feature=+fma` effects on auto-vectorized code; confirm by experiment.
- Rayon: no source retrieved. Known principle (inferred): `par_iter().sum()` / reduce with non-associative f32 ops depends on splitting, which depends on thread count/work-stealing, so reductions must use fixed-shape trees over fixed-size chunks; `collect` into indexed order is deterministic but `reduce` is not. Verify with a test before codifying.

## 3. Cross-platform reproducibility techniques: RNG, reductions, GPU, WASM

### Takeaway
Counter-based RNGs and fixed-shape reduction trees solve scheduling-induced non-determinism; pinned math kernels solve libm differences. GPUs cannot offer bitwise equality with the CPU across vendors, so GPU outputs need their own backend-class key and tolerance checks. WASM is a viable determinism substrate for scalar math but not for relaxed SIMD or NaN bits.

### Cited Findings
- Counter-based RNGs (Salmon et al., SC11 "Parallel Random Numbers: As Easy as 1, 2, 3"): output is a keyed function of a counter, with no sequential state, so they parallelize on CPUs/GPUs/clusters; families ARS, Threefry, Philox; pass TestU01 SmallCrush/Crush/BigCrush; not for cryptography. Random123 is header-only for C/C++/CUDA/OpenCL. — [Random123](https://www.thesalmons.org/john/random123/releases/latest/docs/), [paper PDF](https://users.cs.utah.edu/~hari/teaching/bigdata/random123sc11.pdf), [Wikipedia](https://en.wikipedia.org/wiki/Counter_based_random_number_generator)
- CUDA/PyTorch: nondeterminism arises from the order of parallel `atomicAdd` because float addition is non-associative; seeding does not fix it. Mitigations: sort by key and reduce per segment, defer accumulation to a deterministic sum, or accumulate in double (approximate only). — [PyTorch randomness notes](https://pytorch.org/docs/1.5.1/notes/randomness.html), [PyTorch forum](https://discuss.pytorch.org/t/reproducibility-of-cudaextension/113011/5), [arXiv 2408.05148](https://arxiv.org/pdf/2408.05148)
- WebAssembly nondeterminism list: NaN bit patterns and NaN sign (any NaN-producing arithmetic), relaxed SIMD (nondeterministic), threads/shared memory, host interaction, resource exhaustion (stack, memory); proposed flexible-vectors would make vector length nondeterministic. Core scalar f32/f64 +,-,*,/,sqrt and non-relaxed SIMD are otherwise deterministic. — [WebAssembly Nondeterminism.md](https://github.com/WebAssembly/design/blob/main/Nondeterminism.md)
- Unity Burst `FloatMode.Deterministic` (64-bit only): deterministic math function implementations, disables optimizations that cause platform differences, flushes subnormals to zero; does not guarantee identical NaN representation; costs performance. Older forum posts said cross-platform determinism was unsupported/on hold (outdated). — [Unity docs: float precision and determinism](https://docs.unity3d.com/Manual/burst/float-precision-determinism.html), [Unity forum, state of determinism](https://discussions.unity.com/t/state-of-determinism-in-unity/867770)

### Inferences
- RNG: derive per-element streams as `philox(key=H(node_seed, op_id), counter=(domain, element_stable_id, k))`. Use stable element ids (point id attribute), not loop index after reordering, so edits upstream do not reshuffle randomness unless intended.
- Reductions: define canonical reduction = fixed-size leaf blocks (e.g. 1024 elements) summed sequentially, then a fixed binary tree over blocks; independent of thread count. Alternatively use exact/compensated accumulation (superaccumulator or Kahan-Neumaier with fixed order). Parallel merges (scatter output, bucket joins) must sort by a total order (stable id, then coordinate bits).
- GPU: no sourced claim on driver FMA differences in this pass (see Gaps), but the PyTorch material supports that atomics break reproducibility, and the Rust and Gaffer sources support that FMA/transcendental differences exist across hardware. WGSL permits implementations to fuse multiply-add (inferred from spec knowledge, unsourced here), so treat GPU results as backend-class `gpu:<vendor>:<driver>` keyed, not bit-equal to CPU. Options for a bit-exact GPU path: integer/fixed-point kernels, explicit `fma()` plus pinned polynomial transcendentals, no atomics on floats (use sorted segmented reductions), no subgroup ops in hashed results. Even then, flush-to-zero and rounding of division/sqrt on GPUs can differ (WGSL `/` and `sqrt` accuracy is ULP-bounded rather than correctly rounded; unsourced here).
- WASM: running the pure kernels (and user-plugin nodes, per the plan's WASM plugins) in a WASM runtime with relaxed SIMD off, threads off, and NaN canonicalization on gives a bit-reproducible "portable backend" across x86/ARM hosts. Cost is speed (no AVX-512, limited SIMD to 128-bit). Good as the reference/oracle backend and for plugin nodes; native SIMD remains the fast path with a per-backend-class key.

### Gaps
- No sourced evidence on GPU driver FMA contraction differences or WGSL numeric accuracy rules; read the WGSL spec "Floating Point Evaluation" section and test on NVIDIA/AMD/Intel/Apple.
- Subgroup-op ordering nondeterminism not sourced.
- Rayon behavior not sourced (see above).
- Did not retrieve Unity DOTS-specific determinism writeups beyond Burst docs.

## 4. Existing deterministic engines: what "deterministic" means in practice

### Takeaway
Successful projects claim determinism only for a tested matrix (compilers x architectures) and enforce it with CI hash checks; they all ban or replace transcendentals, disable FMA contraction/fast-math, and control thread-count dependence. They describe it as fragile.

### Cited Findings
- Rapier: "locally deterministic" by default (same machine, same Rapier version and compiler). Cross-platform needs `enhanced-determinism` (cannot combine with `simd8`), strict IEEE 754-2008 targets (including WASM), identical construction/insertion order, and initial-value trig from nalgebra's `ComplexField`/`RealField` rather than `f32::sin`. The `parallel` feature can combine with `enhanced-determinism` and is independent of thread count. — [Rapier determinism guide](https://rapier.rs/docs/user_guides/rust/determinism/)
- Box2D v3 (Erin Catto): no fixed-point; never fast-math; `-ffp-contract=off` on Clang/GCC to disable FMA; custom `atan2f`, `sinf`, `cosf` approximations (because `atan2f` differs across platforms and `sinf`/`cosf` agreement was not trusted); `sqrtf` is deterministic (SSE `sqrtss`). Verified on MSVC/GCC/Clang x64 and ARM via a CI test ("Falling Hinges") each PR; author calls it fragile and notes cross-platform determinism is not rollback determinism. No noticeable performance cost reported. — [Box2D, Determinism](https://box2d.org/posts/2024/08/determinism/)
- Factorio uses deterministic lockstep; a CRC heuristic check runs every tick; on desync a report with both sides' state is written for diffing; a community answer notes older versions had rounding-related desyncs. — [FFF-76](https://factorio.com/blog/post/fff-76), [FFF-188](https://factorio.com/blog/post/fff-188), [FFF-55](https://factorio.com/blog/post/fff-55), [forum thread](https://forums.factorio.com/viewtopic.php?p=212478)
- Burst `FloatMode.Deterministic` (see section 3).

### Inferences
- Recommended definition (the realistic one): bitwise reproducibility within a declared backend-class on a declared platform matrix, verified by CI hash comparison, plus tolerance-bounded agreement across classes. Anything stronger is not supported by the evidence for GPUs and not by libm for CPUs unless we own the math.
- A "diff-of-cooks" tool in the style of Factorio's desync report (first differing node, first differing chunk, first differing element) is cheap with Merkle chunk hashes and should ship with the CI check.
- Our compute is mostly feed-forward, so unlike lockstep sims error does not compound over thousands of ticks; the exception is solvers/loops (erosion iterations, FLIP), where tiny ULP differences amplify and need the strictest class.

### Gaps
- No Factorio primary statement on how they handle float math specifically.
- Did not retrieve Unity DOTS Physics determinism writeups.

## 5. Shared remote caches: security for untrusted agents

### Takeaway
A content-addressed result cache is only as safe as who may write action-result mappings. CAS blobs are self-verifying; action-cache entries (key -> output hash) are claims and are the poisoning surface. For untrusted agents, either execute on trusted workers or partition write namespaces by trust.

### Cited Findings
- Bazel docs: anyone who can write to the cache can influence what others receive; limit writes to CI; cache holds your binaries so must be secured; cleaning a poisoned cache means deleting it (no selective removal per build). — [Bazel remote caching](https://bazel.build/remote/caching)
- Stripe: letting any CI write to a shared cache lets an attacker serve bad binaries to trusted builds; remedy is remote execution on trusted workers so results come from a known environment (with the caveat that it executes untrusted code there). — [Stripe, fast secure builds choose two](https://stripe.com/blog/fast-secure-builds-choose-two)
- jmmv: a remote cache alone is not enough to safely share across users; non-hermetic actions make poisoning hard to detect; client flag `--noremote_upload_local_results` is not a safeguard since enforcement must be server-side. — [jmmv.dev on Bazel remote execution](https://jmmv.dev/2025/09/bazel-remote-execution.html)
- Pigweed added a cache "silo key" to recover from poisoning and allow unsubmitted code to write. — [Pigweed change](https://pigweed.googlesource.com/pigweed/showcase/sense/+/e514c6ae5c9c38dc3e8871654b41c96cefaeb83d)
- CVE-2025-36852 describes a first-to-cache-wins poisoning of bucket-based remote cache extensions (PR artifacts reaching protected branches); NVD status "Awaiting Analysis" at search time and not Bazel-specific. — [CVE entry](https://cvemon.intruder.io/cves/CVE-2025-36852)
- Unreal Zen server is unauthenticated; Epic says restrict to trusted network/VPN. — [Epic DDC docs](https://dev.epicgames.com/documentation/unreal-engine/using-derived-data-cache-in-unreal-engine)
- Nix floating-CA derivations can be rebuilt multiple times to check determinism. — [Nix manual](https://nix.dev/manual/nix/stable/store/derivation/outputs/content-address.html)

### Inferences
- Because our ops are pure and deterministic within a backend-class, we have something Bazel lacks: a cheap verification. A reader (or a sampling auditor) can re-cook a random fraction of hits on a trusted worker and compare hashes; a mismatch quarantines the writer's namespace. This is the "verify suspicious hits" mitigation made systematic.
- Trust tiers: (1) trusted workers write the shared namespace; (2) agents/users write only to per-principal namespaces (silo key), readable by others only after promotion by an audit re-cook; (3) read-only public. Entries should record writer identity, toolchain/op version, and backend-class. CAS blobs are verified by hash on read; manifests verified recursively.
- Op code supplied by users (WASM plugins) must be part of the key by content hash of the module, and executed in a sandbox (WASM already gives memory isolation).
- Privacy: creative assets in cache are confidential; encrypt in transit, authenticate, and avoid unauthenticated Zen-style servers on open networks.

### Gaps
- No evidence retrieved on Houdini or Unity cache-sharing security specifically.
- Large-geometry-specific attacks (hash flooding, oversized chunk DoS) not researched.

## 6. Design recommendations for PLAN.md

1. Two-layer cache. (a) In-process incremental graph à la Salsa (revisions, backdating on output-hash equality, durability tiers). (b) Persistent action cache (`key -> output manifest hash`) over a CAS, Bazel-style. Early cutoff is driven by output manifest hash equality.
2. Key composition (Bet 3 refinement): `H(domain-tag, op_id, op_impl_version, canonical(params), input_manifest_hashes[], seed, backend_class, numeric_profile_version)`. Params canonicalized (f32 bits with NaN/-0 normalized, sorted maps, interned strings by content). Exclude thread count, wall-clock, host paths, env. Include the content hash of any imported file or WASM module.
3. Output = Merkle manifest: per attribute column, fixed-size chunk hashes (BLAKE3), plus topology and group chunks; manifest hash = root. Column-level sharing falls out of Bet 2. Use fixed-stride chunking for columns, FastCDC only for opaque blobs. Hash cost scales with edited chunks via path rehash; hash at write time inside the op while data is cache-hot.
4. Granularity: node-level keys everywhere in Phase 1 (whole-geo). Add per-tile keys only for tiled domains (volumes, heightfields, demand-driven LOD): key = node key plus tile coordinate plus LOD plus halo-input tile hashes. Avoid per-point keys; use chunk-level dirty tracking within a cook instead.
5. Numeric profile (the determinism contract implementation): pinned `hc-math` crate (no `std` transcendentals in cooked paths; clippy/`disallowed-methods` lint on `f32::{sin,cos,tan,exp,ln,powf,powi,...}`), only +,-,*,/,sqrt,`mul_add`; no `algebraic_*`; no fast-math; explicit FMA only via `mul_add` with a fixed expression shape; fixed-shape reduction trees; stable-id sorted merges; Philox with stable ids; NaN rejected or canonicalized at node output; subnormal policy declared (flush at op boundary or document).
6. Backend classes: `ref-cpu` (portable scalar/SIMD-lane-independent, bitwise identical across x86-64/aarch64/WASM, defines truth), `fast-cpu` (wider SIMD but same lane-order semantics; must match `ref-cpu` bitwise where reductions are tree-canonical, otherwise own class), `gpu:<vendor-class>` (own class; tolerance-tested). Keys include the class so classes never contaminate each other. Optionally a "promote" op that re-cooks final results in `ref-cpu` for shared/regression caches.
7. CI: re-cook golden scenes on a matrix (Windows x64 MSVC/GNU, Linux x64, macOS arm64, WASM runtime) and compare manifest hashes; on mismatch print first differing node/chunk/element (Factorio desync-report style). Add property tests that thread counts 1..N yield same hash. Add compile-flag canary test (Box2D "Falling Hinges" analogue) that exercises FMA-sensitive and sum-order-sensitive code.
8. Remote cache: authenticated; per-principal write namespaces plus trusted-worker promotion; sampling auditor re-cooks hits; cache silo key and ability to purge a namespace; GC with TTL > referenced blob TTL (Buck2 lesson).
9. GPU: accept tolerance checking vs `ref-cpu` in CI; pursue bit-exact GPU kernels only for ops where it is cheap (integer/fixed-point, explicit `fma`, no float atomics, no subgroup reductions in hashed results).

## 7. Recommended wording for the determinism contract (for PLAN.md Bet 3 / Section 9)

> **Determinism contract.** Every cook is a pure function of its key: op id and implementation version, canonicalized parameters, input content hashes, seed, and *backend class*. For a given key, the **reference CPU backend** (`ref-cpu`) produces **bitwise-identical output on every supported platform** (x86-64 and aarch64; Windows, Linux, macOS; and the WASM runtime), independent of thread count, scheduling, and cache state. We achieve this by construction: no fast-math or implicit FMA contraction, all transcendentals from a pinned in-repo math library, fixed-shape reduction trees and total-order merges for all parallel work, counter-based RNG keyed by stable element ids, and canonicalized NaN/-0 at node boundaries. Other backend classes (`fast-cpu`, `gpu:*`) are **bitwise-deterministic only for the same class, driver/toolchain stamp and hardware family** and are otherwise guaranteed to agree with `ref-cpu` **within a documented per-op tolerance**, verified in CI. Results from different classes are never mixed under one cache key. The guarantee is verified, not assumed: CI re-cooks golden scenes on the platform matrix and compares Merkle manifest hashes on every change, and a determinism regression is a release blocker. Out of scope: results involving unpinned third-party math, undeclared environment inputs, or NaN payloads.

(Wording choice follows the evidence: Box2D and Rapier claim determinism only for a tested compiler/architecture matrix and call it fragile; Rust documents that its std math is non-deterministic across platforms/versions; GPU reproducibility is undermined by atomics and unspecified math accuracy.)
