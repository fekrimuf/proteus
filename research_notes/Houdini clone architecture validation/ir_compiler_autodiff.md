# IR / Compiler / Autodiff approaches for a graph-to-kernel procedural geometry engine in Rust

Research date: 2026-10-09. Search tool returned mostly snippets; claims below are limited to what fetched pages/snippets support. Anything from my own background knowledge is labelled "background (unsourced)" and placed under Inferences.

## 1. How MLIR, Halide, Taichi, Warp, JAX/XLA, Futhark, Slang and Enzyme do IR, fusion and autodiff; which fits columnar attribute ops, irregular topology, sparse volumes

### Takeaway
Two AD designs are proven for kernel-style code: (a) source/IR-level adjoint generation per kernel plus a light tape across kernels (Warp, DiffTaichi, Slang), and (b) differentiate optimized low-level IR (Enzyme). JAX/Futhark-style array-combinator AD fits pointwise columnar ops but pushes irregularity into special rules. The best model for us is Warp/Taichi/Slang: imperative per-element kernels over columns (a VEX wrangle is exactly one), per-kernel adjoint codegen, and a graph-level tape.

### Cited Findings
- MLIR: SSA IR with dialects, nested regions (preferred over function bodies so loops/conditionals can use dominating values), and "progressive lowering" to target forms; affine maps enable tiling/interchange/fusion; block arguments instead of PHI nodes for compile-time reasons; multithreaded pass manager built on immutable uniqued types — [MLIR Rationale](https://mlir.llvm.org/docs/Rationale/Rationale/)
- MLIR: non-affine control flow is representable but limits polyhedral analysis — [MLIR Rationale](https://mlir.llvm.org/docs/Rationale/Rationale/)
- JAX: jaxprs are explicitly typed, functional, first-order, A-normal-form IR; forward mode via per-primitive JVP rules; `linearize` = jvp + partial evaluation ("unzips" into primal + linear jaxpr); reverse mode = linearize then transpose the linear jaxpr with per-primitive transpose rules; `jit` traces up front ("initial style") and lowers via MLIR/StableHLO to XLA, cached per shape/dtype — [Autodidax](https://docs.jax.dev/en/latest/autodidax.html)
- JAX limit: traced functions cannot use data-dependent Python control flow; batched `cond` becomes `select`, safe only without side effects — [Autodidax](https://docs.jax.dev/en/latest/autodidax.html)
- Halide: algorithm/schedule separation (algorithm has no storage or order; schedule defines order, locality, storage, tiling, vectorization, parallelism); embedded C++, can JIT in-process or compile to object file; backends X86/ARM/RISC-V etc. and CUDA, OpenCL, Metal, D3D12; autodiff published as SIGGRAPH 2018 "Differentiable Programming for Image Processing and Deep Learning in Halide"; autoschedulers published (SIGGRAPH 2016, 2019) — [Halide](https://halide-lang.org/)
- Taichi/DiffTaichi: imperative language with parallel loops and control flow; "megakernel" fusion of stages in one kernel; primal kernel transformed to adjoint kernel by source transformation (output not strict SSA, a simplification pass removes redundant instructions); a lightweight global tape replays gradient kernels in reverse; simulator 4.2x shorter than hand CUDA at similar speed, 188x faster than TensorFlow version — [DiffTaichi, arXiv 1910.00935](https://arxiv.org/pdf/1910.00935) and [summary](https://alphaxiv.org/abs/1910.00935)
- NVIDIA Warp: forward and backward (adjoint) version of each kernel generated by source-code transformation; backward replays forward intermediates; `wp.Tape` records launches and replays in reverse; user allocates outputs; `+=`/`-=` and atomic_add supported, `*=`/`/=` not; each vector component may be assigned once; loops with runtime bounds are NOT replayed in backward (stale intermediates; workarounds: static unrolled loops, preallocated intermediates); write-after-read across/within kernels gives wrong gradients — [Warp differentiability docs](https://nvidia.github.io/warp/stable/user_guide/differentiability.html)
- Futhark: reverse-mode AD implemented as compiler pass over SOACs (map, reduce, scan, reduce_by_index, scatter); rules tuned to preserve fusion opportunities; "accumulators" (needed for adjoints of gathers) lower to atomic updates on GPU, often uncoalesced/conflicting, so suboptimal — [AD for an Array Language with Nested Parallelism, arXiv 2202.10297](https://arxiv.org/pdf/2202.10297); [Reverse-mode AD of reduce-by-index and scan, arXiv 2310.03568](https://arxiv.org/pdf/2310.03568)
- Slang: `fwd_diff` (JVP) and `bwd_diff` (VJP) operators on `DifferentialPair<T>`; `IDifferentiable` types with auto-synthesized `Differential` struct types; `no_diff`/`detach()` to exclude; `[ForwardDerivative]`/`[BackwardDerivative]` custom derivatives; `[PrimalSubstitute]` for body-less intrinsics (e.g. texture sample); loops need `[MaxIters(n)]` or `[ForceUnroll]`; global-resource ops are non-differentiable; side effects may run unspecified times; nested fwd_diff ok, bwd_diff cannot be re-differentiated — [Slang autodiff guide](https://shader-slang.org/slang/user-guide/autodiff.html)
- Slang is Khronos-hosted (moved from NVIDIA); targets SPIR-V, HLSL, GLSL, WGSL, Metal; produces forward and backward derivative code — [Khronos press release](https://www.khronos.org/news/press/khronos-group-launches-slang-initiative-hosting-open-source-compiler-contributed-by-nvidia); HPG 2025 session on Slang built-in autodiff — [Khronos HPG 2025](https://www.khronos.org/events/high-performance-graphics-2025)
- Enzyme: differentiates LLVM IR *after* optimization; geomean 4.2x speedup of AD-on-optimized-IR vs AD-on-unoptimized-IR on ADBench-style suite; works for any LLVM language incl. Rust, MLIR; a reviewer noted missing discussion of limitations/wrong-result cases; SC'21 follow-up does reverse-mode AD of GPU kernels — [Enzyme NeurIPS 2020 (NSF PAR)](https://par.nsf.gov/servlets/purl/10308799); [NeurIPS review](https://proceedings.neurips.cc/paper/2020/file/9332c513ef44b682e9347822c2e457ac-Review.html)

### Inferences
- A VEX wrangle is "one imperative kernel over N elements of columnar attributes" = the Warp/Taichi/Slang model. Adopt per-kernel adjoint codegen; graph-level tape = reverse topological order of node kernels, which is trivially available because we own the node graph (no need for runtime tracing like Warp's Tape).
- Warp's documented pitfalls map to design rules for our IR: (1) make attribute columns write-once per kernel (SSA-style versioned columns) which removes the write-after-read hazard by construction; (2) require static or bounded loops in differentiable snippets (Slang `MaxIters` idea) or checkpoint iteration intermediates in a bounded scratch buffer; (3) adjoint of gather/neighbor reads = scatter-add via atomics (Futhark accumulator, Warp atomic_add), so keep a deterministic non-atomic fallback on CPU.
- Irregular topology (points/prims/vertices with index columns): fits "gather by index column" ops; AD of gather is scatter-add. Sparse volumes (VDB-like): treat as (active-voxel index column + value columns) so they reuse columnar kernels; MLIR/Halide polyhedral/affine machinery is a poor fit for indirect indexing (inference from MLIR's own statement that non-affine access limits analysis).
- Halide's schedule separation is valuable as an idea (graph = algorithm, fusion/tiling choices = schedule chosen by us), but Halide's dense-rectangular-domain assumption is a poor fit for irregular geometry (background, unsourced).
- MLIR is a framework, not an AD or kernel language; adopting it from Rust is heavy (C++ dependency, build cost). Take its ideas (small typed SSA IR, regions/structured control flow, block args) not the dependency (inference).
- JAX-style jvp -> partial eval -> transpose is a clean, well-understood recipe that works on a first-order functional SSA IR; recommended for our IR-level AD (see Q4) since our IR will also be first-order, structured, array-typed.

### Gaps
- Taichi's current (2025-26) project status and its sparse-SNode fusion details were not fetched.
- Slang's autodiff IR transform internals (checkpointing/recompute policy) not found in the guide fetched.
- XLA fusion strategy specifics (loop/input/output fusion) not fetched; only JAX front-end design sourced.
- Halide autodiff internals not available from the page (title only).

## 2. Cranelift JIT in Rust and alternatives (LLVM via inkwell, wasmtime, copy-and-patch, SIMD interpreters)

### Takeaway
Cranelift is a mature, embeddable, fast-compiling backend (order of magnitude faster compile than LLVM, ~14% slower code in one cited paper), with a single-pass regalloc option for even lower latency. I could not source its 2025-26 SIMD/AVX2/AVX-512 status; treat vector width for numeric kernels as something to benchmark in a spike. Copy-and-patch has no mature Rust crate.

### Cited Findings
- Cranelift goals: fast JIT-oriented compile, secure (no UB in IR, fuzzed/verified), ~200k LOC, e-graph optimizer, ISLE DSL for lowering; x86-64, aarch64, s390x, riscv64; used by Wasmtime and experimental rustc backend — [cranelift.dev](https://cranelift.dev/)
- Code generation ~10x faster than an equivalent LLVM system; output ~2% slower than V8 TurboFan and ~14% slower than LLVM-based WAVM (cited paper) — [cranelift.dev](https://cranelift.dev/)
- Wasmtime 28.0 (Dec 2024) added a single-pass register allocator optimized for compile time, user-selectable vs the default runtime-optimized one — [Wasmtime 28.0 notes](https://bytecodealliance.org/articles/wasmtime-28.0)
- Competing TPDE backend reported 4.27x faster compile than Cranelift default regalloc but Cranelift code 1.64x faster (HN thread, June 2025; Wasmtime maintainer: regalloc matters for run-time perf) — [search result, hnrss cfallin](https://hnrss.org/user?id=cfallin) (secondary, snippet only)
- Latest stable per Wikipedia snapshot: Cranelift 0.127.0, 2025-12-22 — [Wikipedia](https://en.wikipedia.org/wiki/Cranelift)
- Copy-and-patch (OOPSLA 2021): stitches precompiled "stencils" with holes, no general register allocator; wasm compiler 4.9-6.5x faster generation than Liftoff and 39-63% faster code; TPC-H SQL code generation two orders of magnitude faster than LLVM -O0; used for CPython 3.13 JIT — [arXiv 2011.13127](https://arxiv.org/pdf/2011.13127); [Wikipedia](https://en.wikipedia.org/wiki/Copy-and-patch)
- No established Rust copy-and-patch crate found; a pgrust ARM64 regex JIT is the only Rust-ish example (secondary) — [search result](https://en.wikipedia.org/wiki/Copy-and-patch)
- OSL (the closest production "shading-language-to-JIT" system): LLVM JIT at render time with precompiled library functions; optimization level controllable to trade compile time vs run time; batched SIMD shading (8/16 points at once for AVX2/AVX-512, since 1.12.6.2) with per-ISA precompiled libs and wide JIT; OptiX GPU path for a language subset — [DeepWiki OSL overview](https://deepwiki.com/AcademySoftwareFoundation/OpenShadingLanguage); [Intel/RenderMan slides](https://www.slideshare.net/IntelSoftware/renderman-the-role-of-open-shading-language-osl-with-intel-advanced-vector-extensions)
- CubeCL has a CPU backend that compiles via LLVM, auto-vectorizes through a `Vector<F,N>` type, and runs on AVX-512 — [CubeCL README](https://github.com/tracel-ai/cubecl)

### Inferences
- Plan the JIT around "SoA loop over a column chunk": the kernel body is scalar per-element code in a tight loop; either (a) emit explicit 4/8-lane vector IR ops in Cranelift if its SIMD is adequate, or (b) emit scalar code and rely on chunked batches. Both options need a spike measuring Cranelift vs LLVM on a representative noise/attribute-math kernel.
- Background (unsourced): Cranelift's 128-bit SIMD is wasm-driven; wider AVX2/AVX-512 lowering is incomplete, so for peak throughput LLVM (inkwell/llvm-sys) wins but costs a large dependency and slower compile. OSL's design (precompiled wide library functions + JIT glue) is the proven way to get SIMD without a great vectorizer: write transcendental/noise/math in Rust compiled ahead-of-time with `std::simd`/portable SIMD, and let the JIT only emit glue and call them.
- Interpreter with SIMD over column chunks (each node/op executes over whole 1024-element chunks) gets most of the win for cheap ops and has zero compile latency; it is the right stage 1 and remains the fallback forever.

### Gaps
- No 2025-26 source found for Cranelift SIMD width (AVX2/AVX-512) or f32x8 support; SIMD-specific compile times not found.
- No sourced Cranelift-JIT use in other numeric/graphics projects in 2025-26 found beyond Wasmtime/rustc_codegen_cranelift.
- inkwell/LLVM compile-latency numbers and wasmtime-as-kernel-host numbers not found.

## 3. WGSL codegen with naga/wgpu: limitations and alternatives (rust-gpu, CubeCL, Slang, ash)

### Takeaway
wgpu is current and actively released (v30.0.1 on 2026-08-21); subgroups exist natively and in browsers (Chrome 134), but f64 and 64-bit atomics have no sourced support. CubeCL already does Rust-kernel-to-WGSL/SPIR-V/CUDA/Metal/CPU with a comptime model and is the closest ready-made fit; Slang is the strongest option if we want a mature compiler with built-in AD.

### Cited Findings
- wgpu CHANGELOG: latest release v30.0.1 (2026-08-21); v29.0.0 (2026-03-18) changed `max_uniform_buffer_binding_size`/`max_storage_buffer_binding_size` from u32 to u64; Metal storage-binding cap at `u32::MAX - 4` restored in unreleased; v28.0.0 (2025-12-17) naga enforces `@must_use` on subgroup builtins; immediates (push constants) aligned to WebGPU spec in v30.0.0 (2026-07-01) with ongoing validation fixes; no entries for f64 or 64-bit atomics — [wgpu CHANGELOG](https://raw.githubusercontent.com/gfx-rs/wgpu/refs/heads/trunk/CHANGELOG.md)
- wgpu v0.20 (2024) added native WGSL subgroup builtins (ballot, reductions, scans, shuffles) behind `Features::SUBGROUP` on Vulkan/DX12/Metal; `SUBGROUP_BARRIER` on Vulkan/Metal; `SHADER_INT64` gives i64/u64 (Vulkan, DX12 w/ DXC, Metal MSL 2.3+) — [wgpu v0.20.0 notes](https://newreleases.io/project/github/gfx-rs/wgpu/release/v0.20.0)
- WebGPU subgroups shipped in Chrome 134 (Feb 2025): request `"subgroups"` feature and `enable subgroups;`; check `subgroupMinSize/MaxSize`; f16 with subgroups needs `shader-f16` — [Chrome 134 WebGPU](https://developer.chrome.com/blog/new-in-webgpu-134)
- CubeCL: single `#[cube]` Rust function compiles on demand to CUDA, HIP, Metal, SPIR-V, WGSL or CPU SIMD; alpha, API may change; IR built in Rust (pliron-based) with LLVM/MSL/SPIR-V/WGSL emitters; comptime specialization, autotune with cached results, compilation cache; tensor cores unavailable on WGSL/CPU; unsupported instruction -> runtime compile error — [CubeCL repo](https://github.com/tracel-ai/cubecl); [Burn 0.17 notes](https://burn.dev/blog/release-0.17.0)
- Burn 0.20 (around Jan 2026) "unifying CPU & GPU kernels with CubeCL", CubeK kernel library, launch overhead moved into JIT phase and cached — [Burn 0.20](https://burn.dev/blog/release-0.20.0/)
- Burn fusion: element-wise, reduction and matmul fusion expanded (0.17) — [Burn 0.17](https://burn.dev/blog/release-0.17.0)
- rust-gpu: SPIR-V/Vulkan target only; "not yet production-ready"; maintained by community since Embark handed over in 2024; WGSL/DXIL only "could" be supported; builds against latest main only — [rust-gpu repo](https://github.com/Rust-GPU/rust-gpu)
- Slang targets WGSL among others (see Q1); a WGSL-specific autodiff maturity statement was not found — [Khronos press release](https://www.khronos.org/news/press/khronos-group-launches-slang-initiative-hosting-open-source-compiler-contributed-by-nvidia)
- Rust `std::offload` (LLVM offload, NVIDIA/AMD) is "will not complete" in its 2025H2 goal; can move data but kernel launch is the next goal — [Rust goals Jan 2026 update](https://goals.rust-lang.org/blog-post-2026-01.html)
- Houdini's own OpenCL nodes: can only modify existing data (no topology creation) and lack higher-level helpers (point clouds, raycasts); forum anecdotes from 2016 — [SideFX forum](https://www.sidefx.com/forum/topic/45685)

### Inferences
- Because WGSL lacks f64 (background, unsourced; consistent with no f64 entries in the changelog), design the IR with f32 as the GPU type and keep an f64 CPU path; do accumulation-sensitive reductions in f32 with Kahan/pairwise or fixed-point u32/u64 (u64 needs SHADER_INT64, native-only).
- Emit WGSL as text from our own IR (small backend, ~one-two thousand lines) is practical and avoids depending on an alpha crate; gate optional features (subgroups, int64, f16) by wgpu `Features` with a portable fallback kernel variant.
- Buffer limit is the portable-compute constraint: default storage binding sizes (128 MiB class, background unsourced) mean columns >limit must be chunked; v29's u64 limit types show the API is moving toward larger values but Metal caps remain.
- Topology-changing ops on GPU need scan/compaction primitives (prefix sum); subgroup ops accelerate these where available, otherwise workgroup-shared-memory scan fallback.
- CubeCL as optional reference/backend is attractive but alpha; recommend writing own IR and using CubeCL only if a spike shows its CPU+WGSL backends cover our op set (decision gate, see plan).

## 4. Rust autodiff options and recommended IR-level AD

### Takeaway
`std::autodiff` (Enzyme) is upstreamed into rustc but still not on nightly as of the Jan 2026 update (Apple hang pending), and it differentiates Rust host code, not user VEX snippets compiled at runtime. For user snippets we must do IR-level AD ourselves (or via Slang/Enzyme-on-LLVM if using an LLVM backend).

### Cited Findings
- std::autodiff: fully upstreamed but not shipped on nightly as of 2026-01-16; CI builds it and artifacts work on Linux; on Apple, any use hangs due to two LLVM copies (rustc + Enzyme); ~5% rustc binary size increase discussed; frontend refactored to a rustc intrinsic; TypeTrees pass Rust layout info to Enzyme; f16/f128 support added; tracked under the "Finish std::offload" goal marked "Will not complete" — [Rust goals Jan 2026](https://goals.rust-lang.org/blog-post-2026-01.html); [Oct 2025](https://goals.rust-lang.org/blog-post-2025-10.html)
- Enzyme works on LLVM IR of any language including Rust and MLIR; differentiates after optimization — [Enzyme paper](https://par.nsf.gov/servlets/purl/10308799)
- Warp, DiffTaichi, Slang and JAX recipes as in Q1 (source/IR transformation; jvp/linearize/transpose).
- Futhark: AD at the level of high-level parallel combinators preserves fusion, vs "differentiating the memory" at low level — [IFL23 paper](https://arxiv.org/pdf/2310.03568)

### Inferences
- Burn autodiff, dfdx, candle are tensor-level tape frameworks (background, unsourced; not researched here); they are a poor fit for per-element imperative snippets with control flow and irregular gathers. I did not find sourced evaluation of them.
- Recommended AD design for our IR (inference from JAX/Warp/Slang): small first-order SSA IR with structured if/for, typed columns; implement (1) forward mode as a dual-number IR transform (cheap, also gives Jacobian-vector products for debugging and gradcheck), (2) reverse mode as JVP -> split into primal+linear -> transpose with per-op rules and a bounded-tape/recompute policy for loops (Slang `MaxIters`, Warp static-loop rules); (3) custom derivative hooks per node/intrinsic (Slang `[BackwardDerivative]`, `PrimalSubstitute`), required for noise, SDF queries, raycasts, sorts; (4) finite-difference/gradcheck test harness (Warp ships `gradcheck`, `jacobian_fd`).
- Non-differentiable ops (topology changes, integer attrs, sorts) get `no_diff` semantics: gradients flow through attribute values only, with topology treated as constant — matches Slang's `no_diff`/`detach` model.
- Run AD *before* fusion but *after* simplification/constant folding (Enzyme's lesson: AD on optimized IR is faster), then fuse forward and adjoint kernels separately.

### Gaps
- No sourced current status of dfdx, burn-autodiff, candle (not searched effectively).
- No date for std::autodiff reaching nightly after Jan 2026; check rust-lang/rust F-autodiff label and goals#109 (the 2026H1/H2 goal list was not retrieved).

## 5. Fusion strategies and when fusion fails

### Takeaway
Pointwise/columnar chains fuse trivially into one loop (Taichi megakernel, Burn element-wise fusion, Halide compute_inline); fusion stops at ops that need cross-element communication or change cardinality.

### Cited Findings
- Taichi/DiffTaichi: programmer-driven megakernel fusion yields higher arithmetic intensity than operator-by-operator tensor libraries — [DiffTaichi](https://arxiv.org/pdf/1910.00935)
- Burn fusion covers element-wise, reductions and matmul — [Burn 0.17](https://burn.dev/blog/release-0.17.0)
- Futhark AD rules chosen to keep fusion opportunities; accumulators (scatter-add) hurt GPU efficiency — [arXiv 2202.10297](https://arxiv.org/pdf/2202.10297)
- Halide: schedule decides where intermediates are computed (inline vs stored) — [Halide](https://halide-lang.org/)
- Houdini VEX is designed to run per element ("SIMD-style" model) — [VEX docs](https://sidefx.com/docs/houdini/vex)

### Inferences
- Fusion barriers for our engine: (1) cardinality-changing ops (delete/blast, fuse points, boolean, remesh) need prefix-sum compaction; fuse the producer pointwise chain *into* the predicate/scan pass and the consumer chain into the scatter pass, but the compaction itself is a barrier; (2) topology-dependent neighbor reads (smooth, relax, point-cloud lookup) require the neighbor column be fully materialized (stencil/halo barrier) — fuse only up to the gather; (3) global reductions/sorts/bounding boxes; (4) sparse volume activation changes (dilation, resample) change the active set; (5) ops reading a column they write (hazards) need versioned columns.
- Practical rule: fuse maximal connected pointwise subgraphs sharing the same domain (point/prim/vertex/voxel class and count); cut at class change, gather, reduction, or compaction; cap kernel size to protect compile latency.
- VEX wrangle snippets are already user-fused kernels; the compiler should inline adjacent pointwise nodes into the snippet IR rather than invoking them as separate loops.

### Gaps
- XLA/TVM/Inductor fusion heuristics not researched with sources.
- No empirical data on fusion benefit for mesh attribute workloads.

## 6. Existing open-source VEX-like languages

### Takeaway
OSL is the best open reference (LLVM JIT, shader-group optimization, batched SIMD, OptiX); Slang is the best open reference for a C-like GPU language with AD; Houdini's VEX is closed and its internals are not documented in the sources I found.

### Cited Findings
- OSL: SPI-originated, LLVM JIT on CPU and GPU, render-time optimization (constant folding, lazy evaluation, shader group transforms), tunable optimization level, batched AVX2/AVX-512 shading, GPU subset via OptiX — [DeepWiki OSL](https://deepwiki.com/AcademySoftwareFoundation/OpenShadingLanguage); [ASWF OSL Annual Review 2025](https://tac.aswf.io/meetings/2025-10-29/ASWF_OSL_Annual_Review_2025.pdf) (listed, not fetched)
- VEX: runs per element over points/prims/voxels; wrangle nodes generate a wrapper kernel that the VEX runtime runs across elements; claimed close to compiled C/C++ performance — [VEX docs](https://sidefx.com/docs/houdini/vex); [Houdini 21 OpenCL/wrangle docs](https://www.sidefx.com/docs/houdini/vex/ocl.html)
- Houdini 21 OpenCL nodes require hand-written kernels (with an @-binding mode injecting load/store boilerplate); community: cannot auto-generate OpenCL from VEX — [Houdini 21 OCL docs](https://www.sidefx.com/docs/houdini/vex/ocl.html); [SideFX forum](https://www.sidefx.com/forum/topic/45685)
- A DNeg paper cites VEX as a JIT success story with task-specific frontend — [DNeg 2018](https://www.dneg.com/wp-content/uploads/2022/11/2018-1.pdf)
- A third-party `vexllvm` project exists (gitee) but its relation to VEX is unconfirmed — [gitee vexllvm](https://gitee.com/s0duku/vexllvm)

### Inferences
- Our own VEX-like frontend (small C-like language: scalar/vec/mat types, `@attr` bindings, `for`/`if`, `foreach` neighbor queries) should lower to our SSA IR; borrow OSL's closure-free subset, the `@P`-style implicit element loop, and the "uniform vs varying" distinction (cheap constant folding and wide codegen).
- Do not start from Slang/OSL's parser: they carry large graphics baggage; a hand-written Pratt/recursive-descent parser is small (background, unsourced). Consider Slang later as an *emit target* (our IR -> Slang text) only if we want its AD and backend breadth for the GPU path.

### Gaps
- No official description of VEX's runtime (LLVM or otherwise) found.
- No open-source VEX-compatible compiler of note found besides the unverified vexllvm.

## 7. Compile-time/latency tradeoffs for interactive editing

### Takeaway
Tiered execution is the proven answer: interpret immediately, JIT in the background, cache by IR hash. Evidence: OSL's tunable optimization level, Cranelift's single-pass regalloc option, copy-and-patch's baseline-tier design, CubeCL's compile/autotune caches.

### Cited Findings
- Cranelift ~10x faster codegen than LLVM; single-pass regalloc option for lowest latency — [cranelift.dev](https://cranelift.dev/); [Wasmtime 28.0](https://bytecodealliance.org/articles/wasmtime-28.0)
- Copy-and-patch intended as baseline JIT tier; orders of magnitude faster codegen than LLVM -O0 in SQL case — [arXiv 2011.13127](https://arxiv.org/pdf/2011.13127)
- OSL exposes optimization-level vs compile-time tradeoff and uses precompiled library functions to cut JIT work — [DeepWiki OSL](https://deepwiki.com/AcademySoftwareFoundation/OpenShadingLanguage)
- CubeCL: compilation cache and autotune cache; autotuning adds first-run overhead; Burn 0.20 moved launch-time specialization into cached JIT — [CubeCL](https://github.com/tracel-ai/cubecl); [Burn 0.20](https://burn.dev/blog/release-0.20.0/)
- JAX caches compiled executables per shape/dtype — [Autodidax](https://docs.jax.dev/en/latest/autodidax.html)
- MLIR designs for compile time (block args, multithreaded pass manager) — [MLIR Rationale](https://mlir.llvm.org/docs/Rationale/Rationale/)

### Inferences
- Make parameters (sliders) runtime uniforms, not constants, so editing a value never recompiles; only edits to snippet text or graph structure recompile. Specialize on shapes/types only (JAX-style key), and hash (IR, target, features) -> cached kernel (in-memory + on-disk).
- Cache per fused-kernel, so editing one node recompiles only its fusion group.
- Run JIT on a worker thread; keep showing interpreter output until the kernel swaps in. WGSL pipeline creation is the dominant GPU latency (background, unsourced), so use async pipeline creation and a pipeline cache.

### Gaps
- No measured end-to-end compile latencies for Cranelift/LLVM on kernels of our size; run a benchmark spike.

## Recommendation (what to adopt vs write) and staged plan

**Write ourselves (core):**
- A small typed SSA IR (first-order, structured `if`/`for`, columnar ops: elementwise, gather, scatter-add, reduce, scan, compact), VEX-like frontend, optimizer (const fold, CSE, DCE, inlining), AD transforms (forward dual, reverse via JVP+transpose with bounded checkpointing, custom-derivative hooks), and fusion pass. Reasons: the sourced AD systems (Warp, DiffTaichi, Slang, JAX) all transform their own IR; no off-the-shelf Rust option differentiates runtime-compiled user snippets; std::autodiff is not yet on nightly and targets host Rust.

**Adopt:**
- Cranelift (`cranelift-jit`/`cranelift-codegen`) for the CPU JIT: fast compile, embeddable, production-hardened, 4 ISAs. Spike SIMD (explicit vector types vs scalar loop over chunk) early; fallback is precompiled `std::simd`/portable-SIMD math library called from JIT glue (OSL pattern). Keep LLVM (inkwell) as an optional "max-performance" tier only if the spike shows Cranelift SIMD inadequate.
- wgpu + our own WGSL text emitter for GPU (portable, actively released: v30.0.1 on 2026-08-21), with optional features (subgroups, int64) behind feature detection.
- Study, don't depend on: Warp/DiffTaichi (AD design), Slang (custom-derivative API design), OSL (batched JIT), Halide (algorithm/schedule split), Futhark (AD that preserves fusion). Evaluate CubeCL as a decision gate (alpha; could replace our WGSL emitter and CPU path if it covers our op set); keep Slang as a possible later emit target for GPU AD.

**Staged plan:**
1. Interpreter: column-chunked SIMD interpreter over the IR (chunks of ~1k elements, `std::simd`/wide). Includes forward and reverse AD on the IR, gradcheck vs finite differences, graph-level reverse tape. Zero compile latency, correctness oracle for later stages.
2. Fusion + CPU JIT: fuse pointwise subgraphs, JIT via Cranelift in background with IR-hash cache; parameters as uniforms; interpreter fallback; benchmark compile latency and SIMD width; decide LLVM tier.
3. GPU: WGSL emitter for the same fused IR (f32, chunked buffers, scan/compact kernels with subgroup fast path); fuse/adjoint kernels emitted from the same AD transform; atomics scatter-add for gather adjoints with deterministic fallback; evaluate CubeCL/Slang gates here.
4. Later: sparse volume kernels, topology-changing ops with compaction, on-disk kernel cache, optional Enzyme/std::autodiff only for host-side Rust nodes once on stable/nightly.

**Unsolved, three routes:** accurate reverse-mode through data-dependent loops with large trip counts. (a) bounded recompute/checkpoint with `MaxIters`-style annotation (Slang), (b) store per-iteration intermediates in preallocated scratch (Warp workaround), (c) user-supplied custom derivative for the loop body or implicit-function-theorem style adjoint for iterative solvers.
